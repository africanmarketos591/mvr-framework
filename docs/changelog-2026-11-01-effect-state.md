# Changelog: 2026-11-01.effect-state.1

This release answers the R8 Enterprise qualification. Its principle is that analysis, institutional authority and execution are three different questions, and that AMOS must answer each one, per exact effect, without letting one rewrite another.

## P0: decision quality

- **Separate states per exact effect (P0.1, P0.2).** `POST /v1/effect-decision` and the licensed MCP tool `mvr_effect_decision` (same body) return, for every requested effect, `analytical_evidence_status`, `institutional_authority_status` and `execution_authorization_status`. Missing authority keeps execution unauthorised without rewriting a favourable analysis; missing permission is never adverse evidence; a favourable analysis never becomes permission. Each effect names its precedence rule, reason codes, controlling and excluded records, dependencies, supported scope, smallest decisive closure with a machine-checkable acceptance condition, accountable role and permitted interim scope. Prohibited and revoked effects close only through the issuer, never "collect more evidence". `dependency_index` maps each claim and record to the effects that depend on it, so a change withdraws every and only its dependents. Contract: `/v1/effect-decision/contract`. Conformance: `conformance/effect-decision/`.
- **Relevance before the workflow starts (P0.3).** Internal non-market work (document formatting and editing, maintenance, scheduling, IT administration) stops `not_relevant` on `mvr_first_call` before any market evidence is requested. Mixed requests carry `effect_split`, so only the relevant effects enter the workflow. A routine label never hides attached claims or evidence.
- **Audit findings (P0.4).** Every audit route returns `audit_findings` (`mvr.audit-finding/1`) and `route_audit_result`. A global hold may stand beside them but never replaces them. The deterministic checks cover dates and freshness, country and locality, load-bearing support, contradiction, revocation and prohibition, unmet conditions, unsupported quantities and organisations, locator precision, directive wording in support, permission laundering and privacy envelope conflicts. Contract: `/v1/audit-findings/contract`. Conformance: `conformance/audit-findings/`.
- **Strict calibration is prospective (P0.5).** `/v1/audit-capabilities` says, before submission, what each audit route performs in each profile and what it depends on. Strict `/v1/evidence-audit` has no certified anomaly model: it answers HTTP 422, `audit_performed: false`, `STRICT_CALIBRATION_MODEL_NOT_CERTIFIED`, non-equivalent alternatives and the structural findings.
- **Model-attributed passage continuation (P0.6).** Licensed responses that issue interpretation tasks now issue a one-time submission slot. Readings go to `mvr_interpretation_submission` (`/v1/interpretation-submissions`), whose complete schema is in `tools/list`, never into a workflow continuation payload. Every reading gets a stable reason code; replay, duplicates, wrong hashes, labels or model identity, receipts used as input, cross-tenant tokens and field mutation each fail for their own reason. Conflicting readings are kept. Only an accountable reviewer disposition changes effect decisions, for dependents only.
- **Content-addressed release identity (P0.7).** `/.well-known/mvr-release-manifest.json` binds the runtime source closure, OpenAPI, licensed and public MCP tool lists, published contracts, policy and contract versions, generated clients, SDK package trees and registry digests, conformance vectors and schemas. Every response names it in `X-MVR-Release-Manifest`. The same file is in `release-manifests/` and attested with a GitHub artifact attestation; `release-drift.yml` checks the live surfaces against it daily.

## P1: market permission substrate

- **Signed origin chain (P1.1).** The lab trust root (`/.well-known/mvr-lab-trust-root.json`, pinned in `trust/amos-lab-trust-root.json`) signs a registry statement per session binding organisation, tenant, realm, assurance, session, keys, validity and endpoints. A receiver verifies root, registry, receipt and current state with `sdks/javascript/trust-chain-verifier.mjs`; cross-session, cross-tenant and cross-realm substitutions fail before any effect.
- **Current-state proofs (P1.2).** `target: current_state` returns a signed reading of one capability (state, dependency heads, policy, sequence, `max_offline_age_seconds: 60`). A receiver commits only if it is permitted, fresh and its heads match; a closed session or unavailable service fails closed.
- **Quota, reset and renewal (P1.3).** Every lab issue carries `issuance_quota` (limit, remaining, reset time, retry interval, scope); a refusal is HTTP 429 with the same fields, `Retry-After` and `RateLimit-*` headers. The per-IP hourly allowance is now four. Clock and renewal rules are published in the lab contract: an expired object is never extended; renewal is a new signed object after a full recheck.
- **Internal dogfood (P1.4).** `conformance/internal-dogfood/` holds the role plan, the 34-case matrix and a live lab rehearsal. The team run with distinct AMOS role holders is not yet run.
- **Verification ledger (P1.5).** Every effect decision carries `verification_ledger`: for each record, the checks performed and not performed, lineage, contradiction, dispositions, assurance derived only from performed checks, and dependents. Nothing is presented as true, authoritative or permitted.

## P2: commercial value

`conformance/r8-evaluation/` freezes the loss weights, gates, event schema, Latin-square allocation and analysis code before any result. The studies that need people are listed there as not run.
